# 09｜额度、质量与流程复盘

## 一、每周记录的指标

| 指标 | 计算或记录方式 | 用途 |
|---|---|---|
| 需求交付周期 | 从 Issue 确认到验收完成的时间 | 找出等待与返工瓶颈 |
| 首次 CI 通过率 | 首次执行即通过的 PR 数 ÷ PR 总数 | 观察任务质量和环境稳定性 |
| Review 有效问题数 | 最终被验证属实的问题数量，按 P0-P3 分类 | 评价审查的实际价值 |
| Review 误报率 | 被验证不成立的意见数 ÷ 已裁决意见数 | 调整提示词与审查范围 |
| 缺陷返工率 | 因实现缺陷而重复修改的任务占比 | 改进需求和测试设计 |
| 发布后缺陷数 | 发布后在观察期内发现且与本次变更相关的缺陷 | 验证质量门禁是否有效 |
| 模型实际费用/用量 | 分别记录每个平台的真实账单或使用面板数据 | 决定是否需要升级付费方案 |
| 单位有效问题成本 | 审查成本 ÷ 验证成立的问题数；没有有效问题时单独记录 | 评估多模型审查是否值得 |

免费额度或平台限制不一定能折算成真实金额。需要分开记录“使用次数/限制体验”和“实际账单”，不要虚构统一成本。

## 二、每周复盘问题

1. 哪些需求因为验收条件不清导致返工？
2. 哪些 Review 发现了真实缺陷？哪些是误报？
3. 哪些缺陷本应在单元测试、集成测试或 CI 阶段发现？
4. 哪个模型在当前任务类型中确实提供了额外价值？
5. 当前编码额度是被长上下文、重复读取、反复重构还是复杂推理消耗？
6. 是否发生过无关改动、工作区冲突、遗漏迁移或回滚困难？
7. 下周只选择哪一个流程改进项，如何验证改进有效？

## 三、判断是否新增付费模型

至少观察一个完整开发周期，比较：

- 主执行者无法解决的任务占比；
- 第二套工具确实解决问题的次数；
- 额外订阅费用和使用量；
- 引入第二执行环境后产生的合并冲突与返工；
- 真实交付周期是否缩短，缺陷率是否下降。

若只有“看起来多了一个模型”，但没有改善交付结果，就不新增订阅。
