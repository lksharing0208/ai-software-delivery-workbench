# 06｜测试与质量门禁

## 一、分层测试策略

| 层级 | 目标 | 常见触发时机 |
|---|---|---|
| 格式与静态检查 | 尽早发现格式、类型、规则和明显缺陷 | 每次 PR |
| 单元测试 | 验证独立业务逻辑与边界 | 每次 PR |
| 集成测试 | 验证数据库、消息、缓存、下游服务等协作 | 影响相应模块时 |
| 契约与接口测试 | 验证请求/响应、错误结构和兼容性 | 接口变更时 |
| 端到端测试 | 验证关键用户流程的整体行为 | 核心链路、发布前 |
| 回归测试 | 防止已修复问题再次出现 | 每个缺陷修复都应评估 |
| 安全与依赖检查 | 发现公开漏洞、危险权限或依赖风险 | 持续或按计划执行 |

## 二、本模板的 CI 做什么

`.github/workflows/质量门禁.yml` 会在 PR、推送到主分支/开发分支和手动触发时运行：

- 检查工作台核心文档是否存在且非空；
- 检查文本文件是否为有效 UTF-8 并以换行符结束；
- 确保必要模板没有被误删。

它是本工作流模板的自检，而不是业务代码测试。把它复制到业务项目后，需要保留或改造自检，并追加对应技术栈真实的构建与测试步骤。

## 三、Java / Maven 项目追加示例

将以下步骤合并进业务仓库的 CI 工作流，并根据项目实际 JDK 版本调整。若项目使用 Gradle，请改为执行实际的 Gradle Wrapper 命令。

```yaml
- name: 设置 Java 环境
  uses: actions/setup-java@v6
  with:
    distribution: temurin
    java-version: '21' # 请与项目实际 JDK 版本保持一致
    cache: maven

- name: 执行 Maven 验证
  run: ./mvnw -B verify
```

Windows 自托管运行器或没有 Maven Wrapper 的项目需要调整命令。不要直接复制示例并假设它适用于当前项目。

## 四、Node.js 项目追加示例

```yaml
- name: 设置 Node.js 环境
  uses: actions/setup-node@v7
  with:
    node-version: '22' # 请与项目版本策略一致

- name: 安装依赖
  run: npm ci

- name: 执行检查和测试
  run: npm run lint --if-present && npm test --if-present && npm run build --if-present
```

请确认项目的锁文件和脚本确实存在。生产级项目应避免因为测试脚本缺失而被误判为测试通过；必要时删除 `--if-present` 并明确要求脚本必须存在。

## 五、Python 项目追加示例

```yaml
- name: 设置 Python 环境
  uses: actions/setup-python@v7
  with:
    python-version: '3.12' # 请与项目实际版本保持一致

- name: 安装依赖
  run: python -m pip install -r requirements.txt

- name: 执行测试
  run: python -m pytest
```

如果项目采用 `pyproject.toml`、Poetry 或其他依赖管理工具，需要将安装步骤改成仓库真实使用的方式。

## 六、生产级门禁要求

- 工作流显式设定最小权限，例如 `permissions: contents: read`。
- 仅在需要部署权限的工作流中配置部署所需权限。
- 为生产环境配置 GitHub Environment 与受限 Secrets，并启用人工审批（具体能力按仓库套餐与组织策略确认）。
- 不在 PR 的不可信代码执行过程中暴露生产密钥。
- 对依赖安装、构建脚本和第三方 Action 保持版本审查，生产环境可按组织要求进一步锁定到完整提交 SHA。
- 将必须通过的状态检查设置为 `main` 合并条件。
- 测试失败时修复根因，不通过删除断言、跳过测试或伪造成功结果绕过门禁。

## 七、测试证据格式

每次变更记录：命令、运行环境、结果、失败摘要、未覆盖场景。示例：

```text
命令：./mvnw -B verify
结果：通过 / 失败 / 未执行
环境：JDK 21，Linux 运行器
备注：集成测试依赖的测试数据库由工作流服务容器提供
```

示例内容须按实际执行结果填写，不得复制示例当作真实通过记录。
