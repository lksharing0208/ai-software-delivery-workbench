# 05｜独立代码 Review 规程

## 一、审查输入必须固定版本

优先向 Reviewer 提供：PR 链接、目标分支、变更分支、提交号、PR 差异，以及与变更直接相关的上下文。网页端必须确认正在审查的是最新提交；不要让它凭仓库旧快照判断新代码。

需要脱敏的配置、日志和业务样例应先在本地处理。不要为方便审查而公开内部仓库或上传全部生产数据。

## 二、审查范围

1. 业务正确性：是否符合需求和验收标准；成功与失败分支是否完整。
2. 数据一致性：事务边界、重复请求、并发、幂等、迁移和历史数据兼容。
3. 接口兼容性：请求/响应结构、错误码、调用方、版本兼容和默认值。
4. 安全：鉴权、授权、敏感信息、输入校验、注入、文件与网络访问边界。
5. 异常与恢复：超时、重试、资源释放、补偿、日志、监控和降级。
6. 性能：不必要的查询、循环调用、锁竞争、内存增长与超大载荷。
7. 测试质量：正向路径、边界、失败路径、回归覆盖和测试是否验证真实行为。
8. 运维：配置迁移、可观测性、部署兼容和回滚方案。

不要机械地对每个小文件套用所有项目；只审查与具体改动相关的风险，并明确哪些检查不适用。

## 三、缺陷报告必须包含

- 严重程度：`P0`、`P1`、`P2` 或 `P3`；
- 文件路径和尽可能准确的行号；
- 触发前提和可复现步骤；
- 当前行为与预期行为；
- 影响范围和风险依据；
- 最小修复建议；
- 可证明修复有效的测试。

不能定位到代码证据、不能说明触发条件的意见，先标记为待验证建议，不直接要求重构。

## 四、处理与裁决

| 结论 | 处理方式 |
|---|---|
| 确认为 `P0` / `P1` | 修复后复测；未解决前阻断合并/发布 |
| 确认为 `P2` | 本次修复或建立有负责人和期限的后续 Issue |
| 属于 `P3` | 由维护者决定是否采纳，不因风格建议扩大改动范围 |
| 证据不足或不成立 | 写清原因；必要时补测试或请 Reviewer 提供复现信息 |
| 多个模型意见冲突 | 回到需求、代码路径、运行结果与测试证据裁决，不采用简单多数票 |

## 五、推荐审查顺序

1. Claude 先独立读差异，避免先受到实现模型解释的影响。
2. 主开发者验证每个问题是否成立。
3. 支付、安全、迁移、并发等高风险变更，再使用 ChatGPT 或 Gemini 交叉审查不同风险面。
4. Codex + DeepSeek 只修复已经确认的问题，并补回归测试。
5. Reviewer 对新差异进行复查，确认原问题关闭且没有引入明显新问题。
6. 将最终结果写入 `templates/Review记录.md`。

## 六、网页端 Review 的权限边界

网页模型通常适合分析和提出建议。除非明确验证当前产品支持、账户已授权且你有意使用写入功能，否则不要把“仓库已连接”视为它能直接推送代码。所有最终修改仍应经过本地差异检查和测试。
