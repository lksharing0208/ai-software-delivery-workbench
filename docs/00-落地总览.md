# 00｜落地总览：从 0 到 1 建好 AI 开发闭环

## 目标

让 AI 辅助开发从“对话里生成代码”升级为可追踪、可复现、可审查和可回滚的软件交付过程。流程必须产出需求、任务、代码差异、测试记录、Review 记录和发布证据。

## 推荐架构

```text
需求提出
  ↓
ChatGPT：需求澄清、架构方案、验收标准
  ↓
GitHub Issue：唯一任务编号与完成定义
  ↓
Codex + DeepSeek：在本地功能分支实现代码
  ↓
本地检查：测试、构建、差异检查
  ↓
GitHub Pull Request：固定本次变更快照
  ↓
Claude：独立 Review；必要时 ChatGPT / Gemini 交叉复核
  ↓
主执行者按已确认的问题修复
  ↓
CI 通过 + 人工验收 + PR 复核
  ↓
合并 main → 部署审批 → 发布验证
  ↓
失败则按已验证的回滚方案恢复
  ↓
记录问题、返工、额度和发布结果
```

## 先落地的最小版本

第一轮只做这些事：

1. 新建私有 GitHub 仓库并推送本工作台。
2. 开启 `main` 分支 PR 保护和 CI 检查。
3. 用一个低风险小功能跑完整闭环。
4. 保存执行任务单、Review 记录和发布检查单。
5. 验证流程可重复后，再拓展到真实业务仓库。

## 责任边界

| 责任 | 主要执行者 | 最终责任人 |
|---|---|---|
| 需求与验收条件 | ChatGPT + 用户 | 用户/产品负责人 |
| 本地实现 | Codex + DeepSeek | 主开发者 |
| 独立 Review | Claude；必要时 ChatGPT/Gemini | 人类审查者 |
| CI 自动检查 | GitHub Actions | 仓库维护者 |
| 合并与生产发布 | 人工操作或受控发布流程 | 发布负责人 |
| 回滚决策 | 人工决策，AI 提供诊断 | 系统负责人 |

## 成功标准

- 新功能可以从 Issue 追踪到 PR、测试结果和发布记录。
- 主分支不能在缺少必要检查的情况下随意合并。
- 每条关键 Review 意见都有“修复、拒绝并说明理由、登记后续”三种处理之一。
- 不存在未授权的生产部署和未经验证的自动重构。
- 能查清本次修改了什么、为什么修改、测了什么、怎样回滚。
