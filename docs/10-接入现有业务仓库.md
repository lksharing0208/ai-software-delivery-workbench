# 10｜把工作流接入现有业务仓库

## 目标

不要强迫所有业务项目采用同一套目录和技术栈。将本工作台作为流程与规范底座，再按项目实际情况接入构建、测试和部署工具。

## 接入顺序

1. 先将 `AGENTS.md` 和 `CLAUDE.md` 合并到项目已有规范中，避免覆盖原有项目约束。
2. 复制最合适的 Issue/PR 模板和 AI 提示词。
3. 在 `README.md` 或 `docs/architecture.md` 中补充真实项目结构、开发环境、构建命令、测试命令和部署方式。
4. 复制质量门禁工作流前，检查它的文件检查清单是否适配目标项目；不要保留错误的路径假设。
5. 增加对应技术栈的真实 CI：格式检查、静态分析、构建、单元测试、必要的集成测试与安全检查。
6. 在 GitHub 中保护主分支并把有效的 CI 状态检查设为必需。
7. 用一个低风险 Issue 试运行；闭环通过后再扩大使用范围。

## 每个项目必须补齐的真实信息

- 技术栈及版本；
- 本地启动命令；
- 构建、测试、格式检查和静态分析命令；
- 配置项名称、必填项和安全来源；
- 关键调用链和业务不变量；
- 测试数据库/外部服务的准备方式；
- 数据迁移步骤；
- 部署步骤、健康检查与回滚命令；
- 不能交由 AI 自动操作的目录或生产操作。

## Java 项目示例清单

请根据项目实际情况确认：

- JDK、Spring Boot、构建工具的具体版本；
- `./mvnw -B verify` 或项目已采用的 Gradle Wrapper 真实命令；
- 单元测试与集成测试的边界；
- 数据库迁移工具和测试数据库设置；
- 测试环境所需的外部服务替身；
- 接口契约、鉴权、事务与并发相关测试；
- 部署制品和数据库迁移的回滚方案。

## 不要盲目复制

模板不能替代项目代码和环境事实。在没有确认项目结构前，不得自动生成不存在的类名、路径、命令、环境变量或部署目标。先读现有实现，再精确地接入。
