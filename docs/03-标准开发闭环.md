# 03｜标准开发闭环：每个需求都走同一条流水线

## 阶段 1：建立需求

每项需求先建立 GitHub Issue，并使用 `templates/需求单.md` 记录目标、现状、用户场景、不做什么、验收条件和风险。没有可验证的验收条件，不进入编码。

## 阶段 2：拆分任务

用 `prompts/01-需求澄清与架构设计.md` 让 ChatGPT 提炼：

- 需求边界和未决问题；
- 受影响模块、接口、数据模型和配置；
- 兼容性与安全风险；
- 验收条件、测试矩阵和回滚方案；
- 可分批完成的任务清单。

把结论写回 Issue 或 `docs/`，不要只留在网页聊天里。

## 阶段 3：建立独立工作分支

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/12-short-description
```

按实际 Issue 编号和任务描述替换分支名。修改前运行 `git status`，确保没有待保护的用户改动。

## 阶段 4：让主执行者实施

将 Issue、方案、相关源码路径、构建/测试命令和 `templates/AI执行任务单.md` 提供给 Codex + DeepSeek。要求它先检查现有实现，按最小差异修改并补测试，不允许假设不存在的接口或依赖。

## 阶段 5：本地验证

至少根据项目技术栈执行：

- 格式或静态检查；
- 编译/构建；
- 与本次变更相关的单元测试；
- 必要的集成测试或契约测试；
- `git diff --check` 和完整差异检查。

记录实际运行的命令、通过/失败结果和未覆盖事项。不能运行的测试必须注明原因，不得将“未运行”写成“通过”。

## 阶段 6：提交 PR

```bash
git diff --check
git status --short
git diff --stat
git diff

git add <本次应该提交的文件>
git commit -m "feat: 增加某项能力"
git push -u origin HEAD
```

在 GitHub 创建 PR，填写仓库中的中文 PR 模板。PR 应聚焦一个目标，并关联对应 Issue。

## 阶段 7：独立 AI Review

1. 让 Claude 审查本次 PR 的精确差异。
2. 高风险任务再让 ChatGPT 或 Gemini 从不同角度复核。
3. Review 模型只给出问题清单，不要求所有模型都生成一套新实现。
4. 对每条意见按 `P0` 至 `P3` 定级并验证；记录修复、拒绝或延期理由。
5. 将已确认的问题交还 Codex + DeepSeek 修改，再重新运行测试和 Review。

## 阶段 8：合并前门禁

检查：

- 自动化检查通过；
- 所有 `P0` / `P1` 关闭；
- 关键讨论已解决；
- 验收条件经人工核对；
- 数据迁移、配置改动和回滚方法已准备；
- PR 只包含预期改动。

合并策略默认使用 Squash and merge，保持主分支历史清晰。

## 阶段 9：发布与复盘

按照 `docs/07-发布与回滚.md` 执行。发布后记录版本、部署人、时间、验证结果、告警和回滚触发条件。按 `docs/09-度量与复盘.md` 汇总有效 Review 问题、生产缺陷、返工和额度消耗。

## 一个可以复用的完成定义

只有同时满足以下条件才算完成：需求可追踪、实现最小化、测试有证据、独立审查有结果、风险已处理、变更已合并、发布有记录、回滚路径清楚。
