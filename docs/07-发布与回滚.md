# 07｜发布、部署与回滚

## 一、发布之前

- PR 已合并到允许发布的分支，所需状态检查全部通过。
- `P0` / `P1` Review 问题全部关闭。
- 人工验收已完成，并记录执行人和结果。
- 数据库迁移已在兼容环境验证；明确迁移前后版本兼容性。
- 环境变量和密钥已由受控渠道提供，未提交到仓库。
- 明确部署批次、监控项、成功条件、失败条件和回滚决策人。
- 对不可逆数据变更、批量任务和付费资源操作单独确认。

## 二、默认发布流程

1. 从已审查并通过 CI 的提交生成可追踪的版本号或构建制品。
2. 在测试或预发布环境先验证关键流程。
3. 通过受控发布流程部署生产；需要时由 GitHub Environment 审批。
4. 验证健康检查、关键接口、日志、错误率和业务指标。
5. 在发布记录中保存提交号、制品版本、部署时间和验证结果。

本仓库不附带自动生产部署工作流，因为尚未提供目标云平台、部署方式、服务名称、密钥和回滚机制。贸然写入部署脚本会造成危险的错误假设。

## 三、回滚预案必须包含

- 触发条件：例如关键业务失败、错误率超过阈值、数据一致性异常或健康检查失败；阈值必须由业务系统定义。
- 回滚对象：应用版本、容器镜像、配置版本、数据库变更和相关任务。
- 执行步骤：明确可执行命令或发布平台操作，并说明权限要求。
- 数据兼容性：代码回滚后能否兼容已经修改的数据结构；是否需要前向修复。
- 验证方式：回滚后执行哪些探针、接口与业务检查。
- 责任人与沟通渠道：谁决定、谁执行、谁确认恢复。

## 四、数据库变更特别约束

优先采用“先增加兼容能力、部署新旧代码可共存版本、迁移数据、观察后再删除旧能力”的分阶段方式。删除字段、修改约束、批量改数据等不可逆变更必须先评估备份、恢复时间和数据核对方案。

不允许仅凭 AI 的口头保证执行生产数据删除或回滚数据库。必须在与生产结构相符的环境中演练并保留记录。

## 五、发布后观察

至少观察关键日志、错误率、响应时间、资源使用与核心业务结果。具体指标由项目定义。如果指标异常，按预案判断继续观察、停止发布或回滚，并记录证据。
