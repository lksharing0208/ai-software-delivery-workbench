# 04｜需求规范与任务拆解

## 需求进入编码前必须回答

1. 要解决谁的什么问题？
2. 当前行为是什么，期望行为是什么？
3. 什么明确不在本次范围内？
4. 怎样证明结果正确？给出具体输入、操作和期望输出。
5. 是否影响接口、数据库、定时任务、权限、费用、数据迁移或历史数据？
6. 出错后怎样发现、定位与恢复？

## 拆分原则

- 一张 Issue 对应一个可以独立验收的目标。
- 优先按业务能力拆分，而不是按模型或文件拆分。
- 单个 PR 尽量控制在一个核心目标；跨模块时在描述中画清调用链或依赖关系。
- 先解决接口与数据契约，再并行开发互不冲突的模块。
- 高风险任务拆为设计确认、实施、测试、迁移/部署等阶段。

## 验收条件写法

推荐使用“给定……当……则……”形式。示例：

- 给定一个已存在且有效的业务订单，当客户端重复提交同一笔请求时，系统不得重复发放权益。
- 给定参数不完整的请求，当接口校验失败时，应返回项目约定的错误结构，且数据库状态不发生变化。
- 给定下游服务超时，当系统重试达到上限时，应有可检索的日志和明确失败状态，不得无限重试。

上述为写法示例，不代表所有业务都应采用这些规则；真实验收条件以项目需求为准。

## AI 输出必须包含

- 需求理解与待确认项；
- 影响模块与现有实现证据；
- 拟修改文件和原因；
- 数据、接口、权限与兼容性影响；
- 测试计划；
- 发布与回滚方案；
- 不在本次范围内的内容。

## 决策记录

对有长期影响的选型、协议、数据模型和权限策略，记录日期、背景、备选方案、选择理由、代价和重新评估条件。不要只在一次聊天中决定架构。
