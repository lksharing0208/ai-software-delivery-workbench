# Requirement & Architecture

## 需求澄清

从用户材料提取：
- 业务目标、参与角色和使用场景；
- 输入、输出、状态流转、边界条件和异常路径；
- 权限、数据隔离、幂等、并发和审计要求；
- 兼容性、性能、可用性和安全要求；
- 验收条件及明确不在范围内的事项。

缺少关键事实时，只询问最重要的一项；不要用假设补齐业务规则。

## 现状分析

1. 阅读相关 Controller/API、Service、Mapper/Repository、Entity/DTO、前端调用、SQL/DDL 和测试。
2. 追踪调用链、事务边界、异常转换、权限校验和数据归属。
3. 复用现有技术栈、项目结构和通用组件；不无故引入框架。
4. 对文档、代码和数据库之间的差异逐项标注证据。

## 方案设计

至少说明：
- 目标与非目标；
- 模块职责及调用关系；
- API 契约、DTO、错误语义和鉴权；
- 数据模型、索引、事务、迁移和回滚；
- 状态机、幂等、并发和失败恢复；
- 测试策略与验收标准；
- 兼容性和分阶段实施计划。

## 约束

不得虚构接口、表字段、枚举、配置或项目依赖。没有真实 DDL/源码支撑的内容必须标记为建议或待确认。
